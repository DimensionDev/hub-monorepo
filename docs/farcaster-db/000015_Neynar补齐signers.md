## 一把公钥怎样变成一行

用“FID + 完整公钥”认一条记录。同一个FID有多把公钥，必须分别处理。

先从 Neynar 读取这个FID的全部链上公钥事件，再只保留要补的公钥。与 source 中同一把公钥的事件合并，按区块号、日志序号排序，复用原有 signers 转换规则。

| target字段 | 实际依据 |
| --- | --- |
| fid、signer | 事件中的FID和原始32字节公钥 |
| app_fid | ADD元数据中的requestFid，按SignedKeyRequestMetadata解析 |
| timestamp | ADD所在区块的时间 |
| deleted_at | REMOVE所在区块的时间；没有撤销时为空 |
| neynar_backfilled | 本功能补入的行是true，原有行是false |
| id | 根据FID和公钥生成固定UUID，重跑保持一致 |
| created_at、updated_at | 首次补入时写入；再次执行不改变 |

`neynar_backfilled=true` 表示这条记录曾用 Neynar 的事件补全。后续普通初始化保留这个来源标记。

缺ADD、元数据解析失败、Neynar与source同一位置事件冲突，都会报错。已有target行与计算结果不同，也不会直接覆盖。

## 怎样运行

在项目目录 `/Volumes/Data/Code/dimension/farcaster-db-convertion` 中运行：

```sh
# 预览最新完成的signers初始化任务留下的缺口
sh scripts/backfill_signers_neynar.sh --report reports/neynar-signers-preview.json

# 确认事件后执行，只写target
sh scripts/backfill_signers_neynar.sh --apply --report reports/neynar-signers-repair.json
```

密钥沿用 `.env.neynar` 的 `<redacted>`，连接沿用 `.env.readonly`。不要把密钥写进命令或文档。

可以加 `--run-id 任务ID` 指定某轮初始化。也可以通过 `--selection-file 文件路径` 提供JSON数组，例如：

```json
[{"fid":123,"signer":"64位十六进制完整公钥"}]
```

CLI每次最多100把，整批同一个事务。记录很多时，用网页“从 Neynar 补齐”的批量任务。

## 网页怎么看

[打开signers页面](http://127.0.0.1:8765/?table=signers)。

“target补齐情况”统计当前筛选的全部历史缺口，显示仍缺公钥和Neynar已补齐。列表给每一把公钥显示当前target状态。侧栏只显示未补齐数量，全部补齐后不再显示18的角标。

“初始化缺口18”及字段分布仍保留，表示那轮初始化当时缺什么。它不代表当前target还少18条。source不补写，因此也不能用source有没有ADD来判断本次补齐是否成功。

“预览本页”能查看完整公钥、应用FID、注册时间、撤销状态和事件。“开始补齐”覆盖当前筛选的全部记录，可按10/25/50/100把分批读取；已有记录会跳过。游标保存FID和公钥，暂停或服务重启后继续，仍会处理同一FID下面的下一把公钥。

任务进度保存到 `reports/neynar-repair-job.json`，旧FID进度文件也能读取。单条失败会留下可导出的记录，继续处理后面的公钥；限流或密钥错误会暂停。
