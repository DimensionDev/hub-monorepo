# fids 分析与实现计划

## 做什么

从 source.onchain_events 的账号事件初始化 target.fids。reference 只提供表结构和索引，不提供业务数据。不修改 source/reference，不改 Shuttle 部署。本轮以源库实际已有数据为范围，缺少历史时明确报告。

## 已查到的结构与来源

reference.fids 有 8 个字段、9 个索引，只有 id 主键，没有 fid 唯一约束。fid 为 integer，其他业务表常为 bigint，要检查范围。custody_address、timestamp 必填，recovery_address、registered_at 可空。字段没有默认 UUID。

读取 type=3、chain_id=10 的账号事件。body.eventType：1 注册，2 转移，3 恢复地址变更。顺序是 block_number、log_index，source.id 只负责扫描顺序；重复链上位置内容相同可以去重，冲突内容必须报错，不能靠 UUID 决定链上结果。错误链、非法地址、越界 FID 明确报错。

注册提供初始 custody、recovery 和注册时间；转移只更新 custody，不清空 recovery；恢复地址变更只更新 recovery。合约 _unsafeTransfer 保留 recoveryOf，这一点已经核对。

## 字段取值

- fid：事件 fid，必须在 PostgreSQL integer 正数范围内。
- custody_address：注册的 to，随后按链上顺序应用 transfer.to；转移的 from 需要与前一状态吻合。
- recovery_address：注册的 recoveryAddress，之后应用 change-recovery。显式零地址保留 20 字节；缺失字段不猜值。
- registered_at：源快照中的 REGISTER 事件时间，不能用采集时间替代。
- timestamp：最近 REGISTER 或 TRANSFER 的区块时间，恢复地址变更不改变这项账号归属时间。这与 Snapchain 的 custody 索引取 REGISTER/TRANSFER 的方式一致；source/reference 共同历史足够时继续核对 reference 口径。
- id：按业务表名与 FID 生成稳定 UUID；已有记录保留 ID。
- created_at：首次写入目标的时间；updated_at 仅在业务字段变化时更新，所有时间用 UTC。

## 缺失与冲突

没有 REGISTER 的 FID 记录为 pending，不创建目标账号、不利用 reference 或现有 target 补成一条看似完整的记录。报告该 FID、原因和具体 missing_fields。以后 restart 读取补齐后的源数据，可以生成该账号。

同一 FID 多条目标记录会报错，不能任意挑选。注册重复或转移链不一致会报错。重新采集到更完整历史时，用保存的链上依据防止旧快照覆盖较新结果；同一历史高水位但正文被修正可以重新计算。

## 命令与恢复

> [!WARNING]
> **已被 shuttle 内联投影取代（见 [100](100_shuttle-inline-projection.md)）**
> 本节描述 Go 一次性 snapshot/init（restart/resume/CLI）的做法，仅作存档；增量现在由 shuttle 在同一事务里内联投影。业务规则以本文其他章节为准。

提供 schema fids、init fids 的预览和 --apply。应用时明确选择 --restart 或 --resume RUN_ID，行为与 blocks 一致：restart 保存新快照，不清空业务表；resume 继续同一快照，已经完成则不再写入，不采集后来新增数据。

fids 任务使用独立的状态范围、快照与锁。不能使 blocks 的旧运行被判为过期，也不能由 fids restart 改写 blocks 的运行状态。写业务记录、保存缺失原因、处理标记与游标在同一事务内提交；失败可恢复，不把失败批次标成已处理。

